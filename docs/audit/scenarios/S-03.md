# S-03 Stale mobile clients: an app build from a year ago still calls the API

Walked 2026-10-08 (Pass 3) against `main` `826b53e`. Method: `methodology.md` Appendix B. New findings are created in their home subject file; this file only walks and references.

## Walk

1. The API is versioned and additive-only under `/api/v1`, with an `X-API-Version` header (documented; `F-ARCH-004` confirms the envelope and error mapping are consistent).
2. A year-old app calls a field that changed meaning, or an endpoint is slow: the client has no timeout, no distinction between offline and server error, sends no client version, and the server has no minimum supported version (F-ARCH-002).
3. Over-the-air updates, forced-upgrade policy and the store release process do not exist (F-REL-005).
4. The authentication path for mobile has never carried a real token, so token changes cannot be tested for old clients (F-AUTH-005).

## Where it breaks

Steps 2 to 4, all covered and trigger-gated at the first mobile build. The additive-only rule is the right foundation and must be enforced by a test when the first real contract exists (F-ARCH-002 recommendation).
