# S-02 One million users: discovery traffic, notifications, location queries, metered cost

Walked 2026-10-08 (Pass 3) against `main` `826b53e`. Method: `methodology.md` Appendix B. New findings are created in their home subject file; this file only walks and references.

## Walk

1. Public discovery is read-heavy. Every page request passes through the identity middleware (`proxy.ts` matches all pages), and reads are not designed to be cheap (F-OPS-003).
2. Location search needs a spatial model and an extension that has not been chosen or checked for availability (F-DATA-008). List endpoints need pagination limits that are undecided (F-ARCH-001).
3. Functions run in US East against a database in US West, adding latency to every query (F-REL-004).
4. Notifications ("Revival coming near you!") fan out to many devices: undesigned, listed as trigger-gated in F-ARCH-001; push and store obligations are in F-REQ-006.
5. Metered vendors (hosting, database, identity per active user) have unknown limits and no budget alerts (F-OPS-003, F-REL-007).
6. Bots and scrapers hit the open APIs: no rate limiting (F-SEC-006).

## Where it breaks

Everything is covered and correctly timed "before public launch" or trigger-gated. The one-owner reality (F-OPS-002) means the first sign of overload would be a bill or a user report (F-OPS-001).

## New

None. Million-user design is correctly not recommended now (F-OPS-005 keeps targets informal).
